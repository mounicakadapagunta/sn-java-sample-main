# Northwind OMS – Smart Build Pipeline

## Overview

The **Northwind OMS Smart Build** project implements a dependency-aware build pipeline for a modular Java and OSGi application using **Python, Maven, GitHub Actions, and Graphviz**.

The pipeline analyzes changes in the repository, identifies the affected OSGi components and their downstream dependents, and builds the selected modules. It also generates dependency graphs, uploads build artifacts, and publishes versioned artifacts to GitHub Releases.

The objective is to reduce unnecessary builds while maintaining dependency-aware build ordering and providing visibility into the application’s component relationships.

## Key Features

* **Change-based builds:** Detects changed files between Git revisions and identifies affected build units.
* **Dependency-aware selection:** Includes downstream dependent components in the rebuild selection.
* **Build ordering:** Uses dependency information to determine an appropriate build sequence.
* **Full build support:** Allows all build units to be selected for a complete build.
* **Maven integration:** Executes the selected Maven reactor projects, including required reactor projects through Maven's `-am` option.
* **Dependency visualization:** Generates Graphviz DOT files and SVG dependency graphs.
* **CI/CD automation:** Runs through GitHub Actions for pull requests, pushes, and manual execution.
* **Artifact management:** Uploads build outputs and dependency graphs as workflow artifacts.
* **GitHub Release publishing:** Publishes matching JAR and ZIP files to GitHub Releases when a version tag beginning with `v` is pushed.

## Architecture and Build Process

The pipeline follows these main stages:

1. **Trigger:** GitHub Actions starts on a pull request to `main`, a push to `main`, a version tag push, or a manual workflow dispatch.
2. **Environment setup:** Checks out the repository with complete Git history and configures Java 17, Python 3.11, Maven caching, and Graphviz.
3. **Build mode selection:** Uses `changed` by default for automated events. A manual run allows the user to choose `changed` or `all`.
4. **Git base detection:** Determines the comparison revision using the pull request base SHA, push event's `before` SHA, or the current `origin/main` SHA for manual runs.
5. **Change analysis:** Runs `smart-build.py` to identify changed build units and calculate the affected dependency closure.
6. **Build execution:** Builds the selected modules using Maven. In changed mode, the selected set is based on the detected changes and dependency relationships.
7. **Graph generation:** Generates full-build and changed-build dependency graphs in DOT format, then renders them as SVG.
8. **Artifact upload:** Uploads available JAR and ZIP files and the generated dependency graphs as GitHub Actions artifacts.
9. **Release publishing:** On a `v*` tag run, publishes matching JAR and ZIP files to a GitHub Release.

## Smart Build Logic

The smart-build script analyzes the OSGi project structure and dependency metadata to determine which components should be rebuilt.

### Changed Build

In `changed` mode, the script compares the current checkout against a specified Git base revision. It identifies changed build units and expands the selection to include affected downstream dependents.

For example, if a shared component changes, modules that consume it may also need to be rebuilt. The resulting selection is ordered according to the dependency graph.

### Full Build

In `all` mode, all discovered build units are selected for the build.

### Dependency Graph

The project uses dependency relationships to visualize connections between components. The graph represents provider-to-consumer relationships, helping developers understand which components may be affected by a change.

The pipeline produces two graph outputs:

* **Full-build graph:** Shows the complete discovered dependency structure.
* **Changed-build graph:** Shows the dependency graph associated with the changed-build analysis.

The graphs are generated in Graphviz DOT format and rendered into SVG for convenient viewing.

## GitHub Actions Workflow

Workflow file:

```text
.github/workflows/smart-build.yml
```

### Workflow Triggers

| Event                                  | Behavior                                                  |
| -------------------------------------- | --------------------------------------------------------- |
| Pull request targeting `main`          | Runs the changed build                                    |
| Push to `main`                         | Runs the changed build                                    |
| Manual `workflow_dispatch`             | Allows selection of `changed` or `all`                    |
| Push of a version tag such as `v1.0.0` | Runs the workflow and enables the release-publishing step |

### Manual Build Modes

When manually starting the workflow from the GitHub Actions tab, select one of the available modes:

* `changed` – analyzes changes relative to the configured Git base and builds the selected units.
* `all` – selects all discovered build units for a full build.

### Workflow Environment

The workflow uses:

* `ubuntu-latest` as the runner
* Java 17 with the Temurin distribution
* Python 3.11
* Maven with dependency caching
* Graphviz for rendering dependency graphs

The workflow checks the installed tool versions before running the smart-build script.

## Build Commands

Run these commands from the `osgi-workshop` directory.

### Changed Build

```bash
python3 smart-build.py \
  --mode changed \
  --base <BASE_COMMIT_SHA> \
  --write-dot build-output/changed-build/dependency-graph.dot
```

Replace `<BASE_COMMIT_SHA>` with the Git revision to compare against.

### Full Build

```bash
python3 smart-build.py \
  --mode all \
  --write-dot build-output/full-build/dependency-graph.dot
```

### Analyze Without Building

Use `--no-build` to inspect the selected build units and generate the graph without invoking Maven.

```bash
python3 smart-build.py \
  --mode changed \
  --base <BASE_COMMIT_SHA> \
  --no-build \
  --write-dot build-output/changed-build/dependency-graph.dot
```

### Generate the Full Dependency Graph Without Building

```bash
python3 smart-build.py \
  --mode all \
  --no-build \
  --write-dot build-output/full-build/dependency-graph.dot
```

### Render a Graph as SVG

```bash
dot -Tsvg \
  build-output/full-build/dependency-graph.dot \
  -o build-output/full-build/dependency-graph.svg
```

The GitHub Actions workflow runs these operations automatically and uploads the generated graph files.

## GitHub Release Publishing

The workflow includes a release-publishing step using `softprops/action-gh-release`.

The publishing step is conditional on a Git tag beginning with `v`:

```yaml
if: startsWith(github.ref, 'refs/tags/v')
```

The workflow uses `GITHUB_TOKEN` and requires repository contents write permission to create or update a release.

### Create and Push a Version Tag

After committing and pushing the required workflow changes, create a version tag:

```bash
git tag v1.0.0
git push origin v1.0.0
```

This triggers the workflow for the tag. If the workflow succeeds and matching JAR or ZIP files are available, the release step publishes them to the GitHub Release.

### Verify the Release

1. Open the repository on GitHub.
2. Select **Releases**.
3. Open the versioned release, such as `v1.0.0`.
4. Verify that the expected build files are attached.

A normal push to `main`, pull request, or manual run on a branch does not satisfy the version-tag condition, so the release-publishing step is skipped for those runs.

## Troubleshooting

| Symptom                                       | What to check                                                                                                                                                |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| No changed modules detected                   | Verify the base SHA and inspect the Git diff between the base and current revisions.                                                                         |
| Too many modules selected                     | Inspect the dependency graph and the transitive downstream dependency closure. A highly connected component can legitimately select many dependents.         |
| OSGi bundle resolution failure                | Check whether the required provider bundle is included in the selected build and whether its exported package version satisfies the consumer's import range. |
| Maven build failure                           | Review the Maven output in the Actions log, especially the first module failure and unresolved dependencies.                                                 |
| Graph not rendered                            | Confirm that the DOT file exists and Graphviz is installed; inspect the `dot` command output.                                                                |
| Release step skipped                          | Confirm that the workflow was triggered by a tag matching `v*`, rather than a branch push, pull request, or manual branch run.                               |
| Release has no expected files                 | Verify that the build generated matching JAR or ZIP files under the module `target` directories.                                                             |
| Release creation fails with permissions error | Verify that the workflow has `contents: write` permission and that repository or organization policies permit release creation.                              |

## Summary

The Northwind OMS Smart Build pipeline automates dependency-aware builds for a modular OSGi application. It combines Python-based change analysis, Maven build execution, GitHub Actions orchestration, Graphviz dependency visualization, workflow artifact storage, and tag-based GitHub Release publishing.

The pipeline provides both changed and full build modes, helping developers inspect component dependencies, run appropriate builds, and distribute versioned build outputs through GitHub Releases.
